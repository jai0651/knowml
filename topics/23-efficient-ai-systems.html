Efficient AI & Systems

Why the same model can cost ten times more to run than it needs to — and the handful of systems ideas that separate a toy inference script from a serving stack that survives real traffic.

Know cold ~24 min · prerequisites: attention & KV cache (08), LLM training basics (10)
TL;DR

Every optimization on this page is either fighting a compute limit or a memory-bandwidth limit — figure out which one you're actually up against before reaching for a fix. Training-time efficiency is about splitting a model and its optimizer state across many GPUs (data, tensor, pipeline, expert parallelism, and ZeRO/FSDP sharding) so you can fit and train something too big for one device. Inference-time efficiency is almost entirely about the KV cache and memory bandwidth: PagedAttention manages that cache without fragmentation, continuous batching keeps the GPU fed instead of idle, FlashAttention removes wasted memory traffic inside attention itself, and speculative decoding trades a cheap extra model for fewer expensive sequential steps. One sentence for an interview: LLM inference is usually memory-bandwidth-bound, not compute-bound, and almost every serving optimization exists to move fewer bytes per useful token generated.

01Where this sits in the timeline

Efficiency wasn't a separate research thread bolted onto transformers afterward — it became unavoidable the moment models and context windows got big enough that naive implementations stopped fitting on real hardware.

Before

Early transformer serving ran the straightforward thing: full-precision forward passes, the full $n \times n$ attention matrix materialized in memory, one fixed-size batch of requests processed start to finish before the next batch could begin. It worked for small models and short sequences. It became wasteful and then simply impossible as context lengths and model sizes grew — the naive approach burns memory bandwidth and GPU idle time that nobody can afford at real traffic volume.

→
Innovation

Three independent insights compounded. FlashAttention (2022) rethought attention around memory-access patterns rather than raw FLOPs — same math, computed without ever writing the huge intermediate matrix to slow memory. PagedAttention, introduced with vLLM (2023), rethought KV cache memory management around OS-style virtual paging instead of contiguous per-request allocations. And continuous batching rethought request scheduling — instead of waiting for an entire fixed batch to finish, slot new requests in and finished ones out on every generation step. None of these needed the others to work, but together they define the modern serving stack.

→
After

Modern LLM serving stacks combine all of the above plus quantization, speculative decoding, and MoE-aware routing — and the field increasingly optimizes for cost-per-token as the actual unit economics of the business, not raw latency in isolation. A model that's 2× faster but not cheaper per useful token served doesn't move the needle the way a genuine cost-per-token win does.

02The intuition, before any math

You are always waiting on one of two things: the GPU's math units, or data moving through memory. Knowing which one tells you which fix actually helps.

A GPU has two separate hard limits. One is how many floating-point operations it can execute per second — its compute throughput. The other is how many bytes it can move between memory (HBM, the GPU's main memory) and the chip's actual arithmetic units per second — its memory bandwidth. Every piece of work you hand the GPU is bound by whichever of these two limits it hits first. If the GPU finishes moving all the data it needs long before it finishes the arithmetic on that data, you're compute-bound — more bandwidth wouldn't help, you need faster or fewer FLOPs. If the GPU finishes the arithmetic almost instantly and then sits idle waiting for the next chunk of data to arrive, you're memory-bound — more compute units wouldn't help at all, you need to move less data or move it faster.

The number that tells you which regime you're in is called arithmetic intensity: how many FLOPs of work you get per byte of data moved. High arithmetic intensity (lots of math per byte fetched) means compute-bound. Low arithmetic intensity (a little math per byte fetched) means memory-bound. Training a large model with big batched matrix multiplications tends to sit on the compute-bound side — you're reusing the same weights across many examples in the batch, so each byte you load does a lot of work. Autoregressive LLM inference, generating one token at a time, is the opposite extreme: each forward step has to drag the entire set of model weights (and the growing KV cache) through memory to compute output for often just a single new token per sequence. Huge byte traffic, comparatively tiny amount of arithmetic per byte. That's why LLM inference is usually memory-bandwidth-bound rather than compute-bound — and it's the single most important systems fact for anyone building or interviewing on LLM serving. It's also exactly why batching helps so much: if you can process 32 requests' worth of tokens against the same loaded weights instead of one, you pay the same memory cost to move the weights once but get 32× the useful compute out of it, pushing you back toward the compute-bound side where the GPU is actually earning its keep.

03Architecture: the modern serving stack, end to end

None of the pieces below are exotic on their own — the insight is how they stack. A request comes in, gets folded into a running batch instead of waiting in a queue, its KV cache lives in non-contiguous pages instead of one reserved block, its attention computation avoids ever writing the full score matrix to slow memory, and — optionally — a small model proposes tokens that the big model verifies in bulk rather than generating them one at a time.

LLM serving pipeline — a request's path through a modern stack
Each stage attacks a different bottleneck: the scheduler attacks GPU idle time, paged KV cache attacks memory fragmentation, FlashAttention attacks wasted memory traffic inside attention, and speculative decoding (dashed, optional) attacks the sequential-step count itself. They compose — production stacks run all four together.

04Training-time efficiency: splitting the model across devices

A frontier model's parameters, gradients, and optimizer state don't fit on one GPU, and even if they did, training on one GPU would take years. The four parallelism strategies below answer different questions about what to split, and real training runs at scale use several of them simultaneously — not because it's elegant, but because each one alone runs into a wall.

Data parallelism is the simplest: replicate the entire model on every GPU, split the training batch across them, run forward and backward independently, then average the gradients before the optimizer step. It scales beautifully as long as the model itself fits in one GPU's memory — the communication cost is just one gradient sync per step. It does nothing to help when the model itself is too big to fit on a single device, which is the situation for every modern frontier LLM.

Tensor parallelism splits individual matrix multiplications across devices — for instance, splitting a weight matrix by columns so each GPU computes part of the output and they exchange partial results mid-layer. You need this when a single layer's weights are too large for one GPU's memory, full stop; there's no way around it with data parallelism alone. The cost is that GPUs now need to communicate within every single layer, which demands very fast interconnects (the devices doing tensor parallelism are usually on the same physical node).

Pipeline parallelism splits layers across devices instead of splitting individual matrix multiplications — GPU 1 holds layers 1–8, GPU 2 holds layers 9–16, and so on, and activations flow through them like an assembly line, one stage handing off to the next. It needs far less communication bandwidth than tensor parallelism (only activations crossing stage boundaries, not mid-layer), which makes it viable across slower links between nodes. The catch is the "pipeline bubble" — early stages sit idle waiting for the first microbatch to reach later stages, and later stages sit idle waiting for the first to start, so you need many microbatches in flight to keep the pipeline full and the idle fraction small.

Expert parallelism is specific to mixture-of-experts models: different experts (separate feed-forward sub-networks) live on different devices, and a router sends each token to only the handful of experts it needs, over the network, mid-forward-pass. This lets you scale total parameter count far beyond what any single accelerator could hold, while keeping the compute per token roughly fixed — you're paying communication cost, not compute cost, for the extra capacity.

Why combine them: at real scale, no single strategy is sufficient on its own. A frontier training run typically uses tensor parallelism within a node (fast interconnect, needed because layers don't fit on one GPU), pipeline parallelism across nodes (slower interconnect, tolerable because only activations cross it), and data parallelism across many copies of that whole pipeline (to actually use thousands of GPUs at once) — sometimes with expert parallelism layered in on top for MoE architectures. Each strategy is solving a different constraint; stacking them is how you turn a few thousand GPUs into one coherent training job.

05ZeRO / FSDP: sharding what data parallelism used to duplicate

Plain data parallelism has a wasteful property: every single replica holds a full copy of the model's parameters, gradients, and optimizer state (which, for Adam, is itself roughly twice the size of the parameters — momentum and variance terms for every weight). For a large model, that redundancy alone can be the thing that makes data parallelism impossible before you even get to compute.

ZeRO (Zero Redundancy Optimizer) — and its widely used implementation, PyTorch's FSDP (Fully Sharded Data Parallel) — attacks exactly that redundancy. Instead of every device holding a full copy of parameters, gradients, and optimizer states, each of those is sharded (split into pieces) across the data-parallel devices. Each device only permanently holds its own shard. When a layer's full parameters are actually needed for a forward or backward computation, the devices briefly gather the missing pieces from each other, use them, and then discard them again rather than keeping a persistent full copy.

What this buys you is significant: you can train models far larger than any single GPU's memory could hold, using ordinary data-parallel-style training, without hand-designing a tensor-parallel or pipeline-parallel split of the model's architecture. It doesn't replace tensor or pipeline parallelism at the largest scales — you still combine them — but it removes a huge amount of unnecessary memory duplication that would otherwise force you into more complex parallelism sooner than necessary. It's usually the first lever pulled before reaching for more architecturally invasive splitting strategies.

06Mixed precision: doing arithmetic in fewer bits

Numbers in deep learning don't need to be stored or computed at the same precision throughout — and using fewer bits is a direct, compounding win: less memory to store and move (which matters enormously given the memory-bandwidth story above), and faster arithmetic, since modern GPUs execute lower-precision matrix multiplications at higher throughput than full FP32.

FP32 (32-bit float) is the traditional default — high precision, high range, but expensive in both memory and compute. FP16 (16-bit float) halves both, but has a narrow exponent range, which means very large or very small values (common in gradients) can overflow or underflow to zero during training — historically requiring a technique called loss scaling (multiplying the loss by a constant before backprop, then dividing it back out) to keep small gradient values representable. BF16 (bfloat16) also uses 16 bits but allocates them differently: it keeps FP32's wide exponent range and sacrifices mantissa precision instead. That wider exponent range is why BF16 tends to be numerically stable for training without needing loss scaling at all — it can represent the same enormous dynamic range as FP32, just less precisely, which turns out to matter far less than range does for training stability. FP8 pushes further still, mostly used for inference and increasingly for training the least precision-sensitive parts of the computation, trading even more precision for even more speed and memory savings.

The pattern used in practice is mixed, not uniform: keep a master copy of the weights in FP32 (or at least higher precision) for the optimizer's accumulation step, where small updates need to actually register — but run the forward and backward pass computations themselves in FP16 or BF16. You get the speed and memory benefit of low precision where it barely costs you anything (the bulk of the matrix multiplications) while protecting the part of training (the accumulation of many small weight updates over time) that's actually sensitive to precision loss.

07Inference-time efficiency: where most interview questions actually land

Training happens once. Inference happens continuously, at whatever your product's traffic is, for the entire lifetime of the model in production — which is exactly why the inference-serving stack gets so much systems attention, and why it's the part of this page you should know coldest.

KV cache growth (the direct callback to page 08)

Page 08 already covered the mechanism: during autoregressive generation, you cache every past token's key and value vectors so you don't recompute them from scratch at every new step. The systems consequence is what matters here — cache size grows linearly with (tokens generated) × (layers) × (heads) × (head dimension), per request, and for long conversations or long contexts this routinely becomes the dominant consumer of GPU memory during serving, often larger than the model's own weights. Every technique below exists because that cache is large, grows unpredictably per request, and has to be managed without wasting the GPU memory it lives in.

PagedAttention

Naive KV cache implementations reserve one contiguous block of memory per request, sized for the maximum sequence length it might reach. Most requests never get that long, so most of that reserved memory sits wasted — and because it's reserved contiguously, that wasted memory can't even be reused for a different request in the meantime. This is exactly the fragmentation problem operating systems solved decades ago with virtual memory paging. PagedAttention, introduced with vLLM, applies the same idea to KV caches: memory is divided into fixed-size blocks (pages), a request's cache lives across possibly non-contiguous blocks, and a block table tracks which physical blocks belong to which logical positions in each sequence. This eliminates fragmentation, lets memory be allocated exactly as needed rather than reserved upfront, and as a bonus makes it cheap to share cache blocks across requests — useful when many requests share a common prefix, like a system prompt.

Continuous batching

Static batching waits for an entire fixed-size batch of requests to finish generating before starting the next batch — but requests finish at wildly different lengths (a one-sentence answer versus a long explanation), so the GPU spends much of its time processing a batch that's mostly finished requests still waiting on one straggler, wasting the freed-up capacity from every request that already completed. Continuous batching (also called in-flight batching) removes that lockstep constraint: at every generation step, finished requests are evicted and new requests from the queue are slotted in immediately, so the batch composition changes continuously rather than being fixed for a whole batch's lifetime. This keeps the GPU close to fully utilized essentially all the time instead of oscillating between busy and mostly-idle, and it's one of the largest practical throughput wins in modern serving — precisely because the earlier intuition holds: more real work per byte of weights moved is exactly what pushes you toward being compute-bound instead of memory-bound.

FlashAttention

Also already introduced in page 08 — worth restating precisely here since this page is where it belongs in depth. FlashAttention computes the exact same attention output as the standard formula; it changes nothing about the math. What it changes is the memory-access pattern: standard implementations compute the full $n \times n$ attention score matrix and write it out to HBM (the GPU's relatively slow main memory) before applying softmax and multiplying by V. FlashAttention instead processes attention in small tiles that fit in SRAM (the GPU's much faster, much smaller on-chip memory), recomputing what it needs on the fly during the backward pass rather than storing the large intermediate matrix at all. It's IO-aware exact attention: same result, dramatically less data shuffled between fast and slow memory — which, given that memory bandwidth is usually the actual bottleneck, translates directly into real wall-clock speedups without any approximation.

Speculative decoding

Autoregressive generation is inherently sequential — token $t{+}1$ needs token $t$ to exist first, so you can't parallelize across the generation steps of a single sequence the way you can parallelize across a batch. Speculative decoding works around this indirectly: a small, cheap draft model proposes several tokens in a row, then the large target model checks all of those proposed tokens in a single parallel forward pass (verification is parallelizable even though generation isn't), and accepts the prefix of proposed tokens that matches what the large model would have generated anyway, rejecting and correcting from the first mismatch onward. The output distribution is provably identical to running the large model alone — this isn't an approximation, it's a mathematically exact sampling procedure that happens to be faster when the draft model's guesses are frequently right, because you get multiple tokens' worth of large-model-verified output for close to the cost of one large-model forward pass.

08The one number that decides everything

$$\text{Arithmetic Intensity} = \frac{\text{FLOPs}}{\text{Bytes moved}}$$
  • FLOPs total floating-point operations the computation performs — the numerator, how much math you're asking the chip to do.
  • Bytes moved total bytes read from and written to memory to perform that computation — the denominator, how much data has to physically travel.
  • Threshold every GPU has a "ridge point" — its peak compute throughput divided by its peak memory bandwidth, in FLOPs/byte. If your operation's arithmetic intensity is above that ridge point, you're compute-bound: the chip's math units are the limiting factor. Below it, you're memory-bound: the chip finishes the math and then waits on data.
  • Practical read operations with a lot of reuse per byte loaded (big batched matrix multiplications, like most of training) sit above the ridge point. Operations that load a lot of data to do comparatively little math with it (single-token autoregressive decoding steps) sit well below it — this is the formal version of "LLM inference is memory-bound."

Keep this conceptual rather than trying to memorize exact ridge-point numbers for specific chips — what an interviewer is actually checking is whether you understand that this ratio, not raw FLOPs or raw bandwidth in isolation, is what determines your bottleneck.

09Why memory bandwidth, not FLOPs, dominates LLM inference

Modern GPUs are built with tensor cores — specialized hardware units purpose-built for exactly one operation: multiply-accumulate on small matrix tiles, extremely fast, in parallel, in a single instruction. They exist because the overwhelming majority of deep learning compute genuinely is matrix multiplication — every linear layer, every attention projection, every feed-forward block reduces to it — so building dedicated silicon for that one operation buys enormous throughput gains over general-purpose arithmetic units. But a tensor core can only run as fast as data actually arrives at it, and that's the constraint that bites during generation.

During training, or during the prefill step of inference (processing the initial prompt before generation starts), you're running the full sequence through the model at once — a large batch of tokens gets multiplied against the same loaded weights, so each weight you fetch from memory gets reused across many tokens' worth of arithmetic before you move on. High arithmetic intensity, comfortably compute-bound.

But during autoregressive decoding — generating tokens one at a time, one per sequence per step — each forward pass has to pull the entire set of model weights (which can be tens or hundreds of gigabytes) and the growing KV cache through memory, to compute output for typically just one new token per sequence. You're paying the full memory cost of moving those weights but getting only a sliver of arithmetic done per byte moved. That's low arithmetic intensity, and it's exactly why single-request autoregressive generation is memory-bandwidth-bound rather than compute-bound: the tensor cores finish their multiply-accumulate work almost instantly and then sit idle, waiting for the next chunk of weights to arrive from HBM. This is precisely why batching multiple requests together helps so dramatically — batching lets you reuse the same loaded weights across many requests' tokens in one pass, raising the amount of useful compute you extract per byte moved, and pushing the operation back toward the compute-bound side of the ridge point where the expensive tensor cores are actually earning their keep instead of idling.

Failure modes worth naming explicitly, because they show up in real deployments and in interview follow-ups. Quantization accuracy loss compounds — dropping weight precision, then also using speculative decoding, then also running a distilled model, each individually reasonable, can stack into a noticeably degraded model if nobody tracks the combined effect rather than each optimization in isolation. MoE routing imbalance is a genuinely hard serving problem: if the router sends a disproportionate share of tokens to a handful of popular experts, those devices become bottlenecks while others sit underused, and the expert-parallel communication overhead of shipping tokens to remote experts can dominate if the routing isn't reasonably balanced. And speculative decoding can backfire: if the draft model's proposals are frequently wrong, you're paying for the draft model's forward passes and getting little acceptance benefit in return — it helps exactly when draft and target agree often, and can slow things down when they don't.

11Compression: quantization, distillation, pruning

Quantization reduces the numeric precision used to store and compute with weights (and sometimes activations) — for example representing weights in int8 or int4 instead of FP16. Post-training quantization (PTQ) takes an already-trained model and quantizes it afterward, with a calibration step that runs a small representative dataset through the model to decide good scaling factors for mapping continuous weight values into the reduced integer range. Quantization-aware training (QAT) instead simulates the effect of quantization during training itself, so the model's weights adapt to tolerate the reduced precision — generally more accurate at very low bit-widths, at the cost of needing to actually retrain or fine-tune rather than just post-process a finished checkpoint. Weight-only int8/int4 quantization works surprisingly well specifically for LLM inference because, given everything above, LLM inference is memory-bandwidth-bound — shrinking the weights shrinks exactly the thing you're bottlenecked on (bytes moved through memory), while leaving activations at higher precision keeps the actual arithmetic reasonably accurate. You get most of the speed and memory benefit without needing to touch the more precision-sensitive parts of the computation.

Distillation trains a smaller "student" model to match the behavior of a larger "teacher" model, typically by training on the teacher's output distribution rather than only hard labels — producing a genuinely smaller, cheaper model rather than a compressed version of the same one. Pruning and sparsity remove weights (or entire structural components like attention heads or neurons) that contribute little to the model's output, either as individual scattered weights (unstructured sparsity, hard to accelerate on standard hardware without specialized kernels) or in aligned blocks (structured sparsity, easier to actually get speedups from). These three techniques are complementary, not competing — a real deployment might run a distilled model that's also quantized and has some structural sparsity applied, stacking savings from three different angles at once.

12MoE serving, edge inference, and deployment tooling

Serving a mixture-of-experts model adds two problems that dense models don't have. Routing imbalance means some experts get far more tokens than others — a purely load-balancing problem, since the router's choices are learned and not guaranteed to be even, and an overloaded expert becomes a serving-time bottleneck no matter how fast the underlying hardware is. Expert-parallel communication overhead means that when experts live on different devices, routed tokens have to physically travel over the network to reach their assigned expert and the result has to travel back — overhead that a dense model, with everything colocated, simply doesn't pay. Both problems are why MoE serving infrastructure is meaningfully more complex than dense-model serving, even though MoE's whole appeal is cheaper compute per token at a given parameter count.

Edge and mobile inference operates under a different constraint entirely: not "how do I maximize throughput across a data-center's worth of GPUs" but "how do I fit and run anything useful within a phone or embedded device's tight memory, power, and thermal budget." That usually means small models to begin with, aggressive quantization (often int4 or lower), and hardware-specific compiled kernels rather than a general-purpose serving framework — the entire optimization target shifts from throughput-at-scale to fitting inside a hard, fixed resource ceiling.

ONNX and TensorRT-style deployment tools sit at a different layer: graph compilation and kernel fusion. A trained model is a graph of many small operations (a matrix multiply, then an activation function, then a normalization, and so on); a naive execution runs each as a separate kernel launch, each with its own overhead and its own round trip to memory for intermediate results. Compiling the graph lets the tool fuse adjacent operations into single kernels (skipping the memory round trip between them) and pick optimized kernel implementations for the specific target hardware — conceptually similar in spirit to what FlashAttention does for attention specifically, but applied generally across an entire model's computation graph.

13Profiling: find the bottleneck before you fix it

The first diagnostic step, always, before applying any optimization from this page, is figuring out whether the workload you're looking at is compute-bound or memory-bound. Profiling tools report GPU utilization, memory bandwidth utilization, and time spent in each kernel — if compute utilization is high and bandwidth utilization is low, you're compute-bound and should be looking at reducing FLOPs (smaller model, fewer layers, algorithmic changes) or using faster numeric formats. If it's the reverse — bandwidth near its ceiling while the compute units sit idle — you're memory-bound and should be looking at reducing bytes moved (quantization, better batching, KV cache management) rather than trying to speed up arithmetic that was never the bottleneck. Applying a compute-side fix to a memory-bound problem, or vice versa, is a common and completely avoidable mistake — profile first, optimize second.

14Worked example and a production use case

Illustrative arithmetic-intensity calculation

Take a single attention operation during one autoregressive decoding step, generating one new token, attending back over a KV cache of length $n$, with head dimension $d$. The computation is dominated by two matrix-vector products: the new query against all cached keys, and the resulting attention weights against all cached values. Roughly, that's on the order of $4nd$ FLOPs (illustrative, rounding off constants). The data that has to move through memory is the entire KV cache: $2nd$ values (keys plus values), each some number of bytes depending on precision — say 2 bytes for FP16, so $4nd$ bytes moved (illustrative). Arithmetic intensity works out to roughly $4nd / 4nd \approx 1$ FLOP per byte moved — far below the ridge point of any modern GPU, which typically needs on the order of 100+ FLOPs per byte to be compute-bound. This tiny illustrative calculation reproduces the real-world finding: single-request decode-step attention is deeply memory-bound, because you're moving the entire cache through memory to do very little arithmetic with each piece of it.

Production use case: sizing a chat product's serving deployment

Say you're standing up serving infrastructure for a chat product. The KV cache budget per GPU determines your practical concurrency ceiling — figure out your model's per-token cache size (layers × heads × head_dim × 2 for K and V × precision in bytes), multiply by your target max context length and expected concurrent conversations, and that tells you how much GPU memory is spoken for by cache alone before you've served a single extra request beyond what fits. Continuous batching then determines how efficiently you use whatever concurrency that budget allows — with static batching you'd be leaving a large fraction of GPU time on the table waiting for stragglers; with continuous batching you keep the batch close to full essentially all the time. PagedAttention lets you actually hit that KV cache budget without wasting memory on over-reserved, under-used contiguous blocks, and lets you cheaply share cache for a common system prompt across many concurrent users. Put together, these choices are what determine your realized throughput (tokens served per second per GPU), which combined with your GPU's hourly cost gives you cost-per-token — the number that actually determines whether the product is economically viable at the traffic you expect, not just whether any single request feels fast in isolation.

15Interview questions

BeginnerIs LLM inference compute-bound or memory-bound, and why does that matter?

Autoregressive decoding is usually memory-bandwidth-bound, not compute-bound. Each generation step moves the entire set of model weights (and the growing KV cache) through memory to compute output for typically just one new token per sequence — a lot of bytes moved for comparatively little arithmetic, i.e. low arithmetic intensity, which lands you below the GPU's compute/bandwidth ridge point. It matters because it tells you which class of optimization actually helps: reducing bytes moved (quantization, better cache management, batching) helps a memory-bound workload; reducing FLOPs alone does not, since the tensor cores were already sitting idle waiting on data, not on math.

BeginnerWhat is arithmetic intensity, in plain terms?

FLOPs of computation divided by bytes of data moved to support that computation. High arithmetic intensity means you're doing a lot of math per byte fetched, which tends to be compute-bound. Low arithmetic intensity means you're fetching a lot of data to do comparatively little math with it, which tends to be memory-bound. It's the single number that tells you which of the GPU's two hard limits — compute throughput or memory bandwidth — you're actually up against for a given operation.

IntermediateExplain PagedAttention and why it matters for serving.

Naive KV cache allocation reserves one contiguous block per request sized for the worst-case sequence length, which wastes memory (most requests don't reach that length) and fragments memory (that reserved space can't be reused for other requests in the meantime). PagedAttention, from the vLLM paper, borrows the OS virtual-memory idea of paging: the cache is divided into fixed-size blocks, a request's cache can live across non-contiguous blocks, and a block table tracks the mapping. This eliminates fragmentation, lets memory be allocated on demand rather than reserved upfront, and enables efficient sharing of cache blocks across requests — e.g. a shared system prompt — which directly increases how many concurrent requests you can serve out of a fixed pool of GPU memory.

IntermediateWhy does continuous batching improve GPU utilization over static batching?

Static batching waits for every request in a fixed batch to finish generating before starting the next batch, but requests finish at very different lengths — so for much of the batch's lifetime, the GPU is doing useful work for only the few requests still generating while capacity freed up by finished requests sits unused. Continuous batching evicts finished requests and admits new ones from the queue at every generation step instead of at fixed batch boundaries, keeping the batch close to full essentially continuously. Since memory-bound decode steps benefit hugely from batching (more useful compute extracted per byte of weights moved), keeping the batch full translates directly into much higher realized throughput.

IntermediateWhy does speculative decoding not change the output distribution, even though it's using a different, smaller model to help?

The draft model only proposes candidate tokens; it never gets to unilaterally decide what's actually output. The large target model verifies every proposed token in one parallel forward pass and only accepts a proposed token if it matches (via an exact, correct acceptance/rejection procedure) what the target model itself would have sampled. Anything the target model wouldn't have produced gets rejected and regenerated from the target model directly. The math guarantees the final sampled sequence has exactly the same distribution as running the target model alone — the draft model only affects how many large-model forward passes you need, not what gets generated.

DeepDesign a cost-efficient serving system for a high-traffic chat product. What do you actually decide, in order?

Start by profiling to confirm you're memory-bound at your expected sequence lengths and batch sizes — that dictates the rest of the priorities. Pick a quantization level (often int8 weights, sometimes int4) that shrinks memory traffic without unacceptable quality loss, calibrated on representative data. Use PagedAttention-style KV cache management sized against your target max context and expected concurrency, so memory isn't wasted on over-reserved blocks. Run continuous batching so the GPU stays close to fully utilized instead of oscillating with request completions. Use FlashAttention-class kernels so attention itself isn't burning extra memory bandwidth beyond what's structurally necessary. Consider speculative decoding if you have a cheap, reasonably accurate draft model available and users are latency-sensitive. Then measure realized tokens/second/GPU under realistic traffic, multiply by GPU hourly cost, and that gives cost-per-token — the number to actually optimize against, since it captures throughput, latency, and hardware cost together rather than any one of those in isolation.

DeepYou quantize a model, add speculative decoding, and serve a distilled version of it — and quality drops more than any single change would predict. What's going on, and how do you debug it?

Each optimization was validated in isolation, but their errors can compound rather than simply add: a distilled model already approximates the teacher's behavior, quantizing it further compounds that approximation, and if the draft model used for speculative decoding was itself calibrated against the original full-precision model, its acceptance behavior may now be miscalibrated against the new quantized-distilled target, changing acceptance rates and effectively changing what gets generated in edge cases. Debug by isolating variables — evaluate the distilled model alone, then distilled+quantized, then the full stack with speculative decoding, at each step measuring quality on the same eval set, to find where the compounding actually happens rather than assuming it's evenly distributed across all three changes.
