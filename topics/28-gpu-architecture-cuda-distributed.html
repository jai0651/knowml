GPU Architecture, CUDA & Distributed Training

What a GPU actually is, why its hardware fits neural network math almost by accident, and the physical communication layer underneath every distributed training run — SIMT cores, warps, tensor cores, CUDA, Triton, NVLink, and ring all-reduce.

Know cold ~25 min · prerequisites: Efficient AI & Systems (23), Attention & Transformers (08)
TL;DR

A GPU is thousands of simple cores built to execute the same instruction across thousands of pieces of data at once — SIMT, single instruction multiple threads — which is exactly the shape of dense matrix multiplication, the operation that dominates deep learning compute. Warps of 32 threads execute in lockstep, tensor cores fuse whole small-matrix multiply-accumulates into one hardware operation, and CUDA lets you write a kernel from a single thread's point of view while the hardware runs that same code across a grid of thread blocks; Triton exists because writing that CUDA well — coalesced memory access, enough resident warps to hide memory latency — takes deep, specialized expertise that most ML researchers don't have and, increasingly, don't need. Scale training beyond one GPU and the bottleneck moves from compute to communication: NVLink connects GPUs on the same node at very high bandwidth, InfiniBand connects nodes at meaningfully lower bandwidth, and ring all-reduce is the algorithm that keeps gradient synchronization from becoming the bottleneck as you add more GPUs, because each GPU only ever sends and receives a bounded amount of data, independent of cluster size. One sentence for an interview: GPUs win at deep learning because SIMT hardware matches dense matmul's shape almost perfectly, and distributed training scales because ring all-reduce turns gradient synchronization into a communication cost that doesn't grow with the number of GPUs.

01Where this sits in the timeline

None of this hardware was designed for neural networks in the first place. The fit between GPUs and deep learning is one of the more consequential accidents in computing history — and understanding how it happened tells you a lot about why the hardware looks the way it does today.

Before

Neural networks were trained on CPUs, or on early GPUs that were never built with this workload in mind — they existed to rasterize triangles and shade pixels for real-time graphics. Getting general-purpose numerical computation to run on them meant disguising your math as a rendering problem. There was no dedicated deep learning tooling, no purpose-built matrix-multiply hardware, and no real framework for treating a GPU as a general-purpose parallel computer rather than a graphics accelerator.

→
Innovation

CUDA (2007) gave programmers a general-purpose way to run arbitrary parallel code on a GPU without pretending it was a graphics workload — the first time GPUs became a genuine general-purpose compute platform. cuDNN and tensor cores (tensor cores arrived with the Volta architecture in 2017) added library- and hardware-level support specifically for the matrix-multiply-heavy shape of deep learning. Around the same time, ring all-reduce — Baidu's 2017 application of a decades-old high-performance-computing technique to gradient synchronization — solved a scaling problem that had nothing to do with any single GPU's speed: how do you average gradients across hundreds of GPUs without one central link becoming the bottleneck? Horovod (2018) popularized that approach as an easy-to-adopt library. And Triton — first described in a 2019 academic paper, then open-sourced by OpenAI in 2021 — made most of hand-tuned CUDA's performance reachable without years of CUDA-specific expertise.

→
After

Frontier model training now runs on thousands of GPUs spread across many physical nodes, with parallelism strategies chosen specifically around the interconnect topology underneath them. Hardware- and kernel-level efficiency work — the direct continuation of what page 23 covers — is as central to training and serving frontier models today as any purely algorithmic idea. The systems layer stopped being an implementation detail a while ago; at this scale, it's load-bearing.

02The intuition, before any math

A GPU is a factory floor with thousands of simple, identical workers, each doing the same small step of the same job at the same time. A CPU is a handful of extremely capable generalists, each able to do a completely different, complicated task, including deciding what to do next based on what just happened.

A CPU core is built to run a long, branchy, sequential program fast. It has deep pipelines, branch predictors, out-of-order execution, and a lot of on-chip logic dedicated purely to guessing what instruction comes next and recovering cheaply when the guess is wrong. That's an enormous amount of silicon spent on control flow, and a CPU only has a handful of these very capable cores — tens, not thousands. A GPU makes the opposite bet: it gives up almost all of that control-flow machinery and instead packs thousands of small, simple cores onto the same chip, all of which execute the exact same instruction at the exact same time, just on different pieces of data. That architecture has a name — SIMT, single instruction, multiple threads. It's a terrible fit for a workload full of unpredictable branches, because every one of those thousands of cores has to be doing the same thing at once. But it's close to a perfect fit for a workload that's the same simple arithmetic operation repeated an enormous number of times over different numbers — which is exactly what deep learning is.

Look at what a neural network's forward pass actually does at the arithmetic level: matrix multiplications and elementwise operations, over and over, layer after layer. A matrix multiply is thousands or millions of independent multiply-and-add operations — every output element depends only on one row and one column of the inputs, none of those computations depend on each other, and there's essentially no branching anywhere in it. That's an embarrassingly parallel workload in the literal technical sense: parallelizing it requires no cleverness and no communication between the parallel pieces, just doing the same tiny operation many times over. It's exactly the workload SIMT hardware was built for — and it's the real reason GPUs, originally built to compute pixel colors, which is also an enormous number of small independent identical computations, turned out to be the right hardware for neural networks almost by accident.

03Architecture: from the code you write to the silicon that runs it

The factory-floor picture is the intuition. Here's the actual hierarchy — both in the code you write and in the physical hardware that executes it. They mirror each other almost exactly, which is the entire point of the CUDA programming model: you describe work in software terms, and the hardware structure underneath was built to match.

The CUDA execution hierarchy — software concepts mapped onto physical hardware
Each level on the left has exactly one physical counterpart on the right — this is the literal execution model, not an approximation. A kernel launch is a grid of thread blocks; each block is assigned to one streaming multiprocessor for its whole lifetime; each block's threads are grouped into warps of 32, and the SM's warp scheduler issues one instruction to one warp per cycle; each thread's instruction actually runs on one core. You write the kernel once, from a single thread's point of view — the hardware is what turns that into thousands of simultaneous executions.

That last point is the mental model worth sitting with: CUDA code is written from one thread's perspective. Inside the kernel you ask "which piece of the problem am I" — using built-in indices for which block and which thread within the block you are — and the hardware launches that exact same function across every thread in the grid simultaneously. You never write a loop over threads; the loop is the hardware itself, running your one function body thousands of times over, in parallel, each copy seeing a different index.

04The memory hierarchy: where page 23's bandwidth story physically lives

Page 23 built its entire framing around one fact: LLM inference is usually bottlenecked by memory bandwidth, not compute. This section is about where that ceiling actually comes from — the chain of physical memory a GPU has to move data through, fastest and smallest at one end, slowest and largest at the other.

Registers sit closest to the arithmetic units and are private to a single thread — the fastest memory on the chip, and there's very little of it per thread. Shared memory (sometimes described together with L1 cache, since they occupy the same physical on-chip pool on most architectures) is private to one streaming multiprocessor and shared among the threads of a block running on it — still extremely fast, still small, but large enough to hold a working tile of data that many threads in the same block need to reuse. This is precisely the memory FlashAttention deliberately tiles its computation to fit inside, so intermediate attention scores never have to leave it. L2 cache is shared across the entire chip rather than one SM — bigger than shared memory/L1, but a further step down in speed. And HBM, the GPU's main memory, holds everything: the model's full set of weights, activations, and the KV cache during inference. It's enormous compared to what's above it in this hierarchy, and it's comparatively slow to reach — it's the thing you're actually bottlenecked on during a memory-bound decode step.

GPU memory hierarchy — small and fast at the top, huge and slow at the bottom
Registers and shared memory/L1 live physically inside each streaming multiprocessor — private to it, and about as fast as on-chip memory gets. L2 is shared across the whole chip: larger, slower. HBM sits off the compute die entirely — huge capacity, by far the slowest tier to reach. Every "memory-bound" claim on page 23 is really a claim about the gap between the top of this stack and the bottom.

05Streaming multiprocessors, warps, and warp divergence

A streaming multiprocessor, or SM, is the basic physical building block of a GPU — one chip contains dozens of them, each with its own chunk of cores, its own warp scheduler, its own register file, and its own shared memory/L1 pool. SMs operate largely independently of each other; a thread block, once assigned to an SM, stays there and runs using only that SM's local resources.

A warp is a group of 32 threads that the hardware always schedules and executes together — the same instruction, at the same time, just on different data. It's the actual physical unit of SIMT execution, one level below the thread block you write your code in terms of. Whatever a thread block's size is, the hardware internally splits it into warps of 32 and issues instructions warp by warp.

Warp divergence is what happens when threads inside the same warp need to take different branches of an if/else. Say 16 of the 32 threads in a warp satisfy some condition and the other 16 don't. Because a warp can only execute one instruction stream at a time across all of its lanes, the GPU can't run both branches simultaneously for different threads — it serializes them. First it runs the "if" branch's instructions across the whole warp, masking off the 16 threads that shouldn't be doing that work so their results don't get written. Then it runs the "else" branch's instructions across the whole warp, masking off the other 16. Every thread in the warp sits through both branches; only half the work in each pass is actually useful. That's why branch-heavy, data-dependent control flow is slow on a GPU — and it's exactly what dense matrix multiplication and elementwise operations avoid almost entirely, since every thread in every warp is doing the identical instruction on different numbers, with essentially nothing to diverge on.

06Tensor cores: dedicated hardware for matrix multiply-accumulate

A regular CUDA core does general-purpose arithmetic — useful for a huge range of operations, but not specialized for any one of them. A tensor core is different: it's a separate, purpose-built piece of hardware, alongside the regular cores on the same SM, that does exactly one thing extremely fast — a fused multiply-accumulate on small tiles of matrices, computed as a single hardware operation rather than as a sequence of individual multiplies and adds.

This is the literal hardware reason mixed-precision training, covered on page 23, runs faster rather than merely smaller. Reducing precision from FP32 to FP16 or BF16 shrinks the bytes you have to move — that's the memory-bandwidth half of the story. Tensor cores are the other half: they execute matrix multiplication at these reduced precisions at dramatically higher throughput than the general-purpose cores achieve, even at matched precision. Training in FP16 or BF16 isn't just about fitting more into memory — it's routing your matrix multiplies onto hardware that is specifically, physically built to be fast at exactly that operation, at exactly that precision.

07The CUDA programming model: kernels, occupancy, and hiding latency

A kernel is a function you write once and launch across a grid of thread blocks — the diagram above showed the shape of it. Each block gets assigned to one SM, and within that block, many warps of 32 threads each get scheduled onto that SM's cores. The mental shift, coming from ordinary sequential programming, is that you don't write a loop over the data — you write the body of the loop, from one thread's point of view, and the hardware runs that body across every thread in the grid at once.

Occupancy is how many warps can be resident on an SM at the same time, out of some hardware maximum. It's determined by how much of the SM's limited register file and shared memory each thread block consumes — a kernel that uses a lot of registers or a lot of shared memory per thread fits fewer blocks (and therefore fewer warps) onto an SM simultaneously; a lean kernel fits more.

Occupancy matters because of what happens when a warp stalls. If a warp issues a memory request to HBM — slow, relative to the chip's arithmetic throughput, exactly as the memory hierarchy above lays out — it has to wait for that data to come back before it can keep computing. A warp scheduler with only one resident warp just sits idle during that wait. A warp scheduler with many resident warps instead switches to a different warp that has work ready to go, right away, for that cycle — hiding the first warp's memory latency behind another warp's useful compute. That's the entire point of occupancy: more resident warps gives the scheduler more options to hide latency behind. Push a kernel's register or shared-memory usage too high, fewer blocks fit on an SM, occupancy drops, and the SM starts genuinely idling waiting on HBM instead of hiding that wait — which is exactly the failure mode you're trying to avoid, given how slow that bottom tier of the memory hierarchy is relative to everything above it.

08Triton: why most people no longer hand-write CUDA

Writing genuinely efficient CUDA requires exactly the expertise laid out in the last two sections at once — coalesced memory access patterns so a warp's threads read contiguous, aligned memory instead of scattering many small requests across HBM, careful register and shared-memory budgeting to keep occupancy high, and correct manual thread-indexing math for every kernel you write. Getting all of that right simultaneously is a genuinely specialized skill, closer to hardware engineering than to the tensor-and-layer thinking most ML researchers actually work in — and building a new hand-tuned CUDA kernel for every new idea is a real cost most research doesn't have time to pay.

Triton exists to remove that cost. It's a Python-embedded language and compiler where you write kernels at the level of tiles or blocks of data rather than individual threads — you describe the computation on a block of, say, 128 elements at once, using ordinary-looking array operations, and Triton's compiler automatically handles the low-level thread scheduling, memory coalescing, and shared-memory allocation that you would otherwise have to hand-tune in raw CUDA. It doesn't always match what a world-class hand-written CUDA kernel achieves in every case, but it routinely gets close — a large fraction of hand-tuned CUDA's performance, for a fraction of the development time and specialized expertise that hand-tuned CUDA demands.

This isn't a hypothetical tradeoff — it shows up directly in tooling you've probably already used. FlashAttention's efficient reference implementation is written in Triton. A large and growing share of PyTorch's own generated custom kernels are Triton kernels. OpenAI open-sourced Triton in 2021 specifically because it hit that performance-per-engineering-hour tradeoff well enough to be worth building an entire compiler around.

09The interconnect hierarchy: NVLink, InfiniBand, and Ethernet

Everything so far happens inside one GPU. Distributed training needs GPUs to talk to each other, and the physical link they talk over matters enormously — it's a completely different bottleneck from anything discussed above.

Within one node, GPUs communicate over NVLink — a direct, very high-bandwidth link built specifically for GPU-to-GPU communication, roughly hundreds of GB/s (approximate, and it varies by generation of hardware). Between nodes, GPUs communicate over InfiniBand, or RoCE (RDMA over Converged Ethernet, which achieves similar low-latency direct-memory-access behavior over Ethernet-like hardware) — still fast, purpose-built for high-performance computing and large training clusters, but roughly an order of magnitude or more below NVLink's bandwidth. Plain Ethernet without RDMA is the slow path: general-purpose networking, higher latency, lower throughput, fine for cluster coordination and logging traffic but not built to carry the volume of data distributed training needs to move between every synchronization step.

This directly drives how you place a training job's parallelism strategies onto physical hardware. Tensor-parallel shards exchange partial results within every single layer — many times per forward pass and many times per backward pass — so they need to sit on GPUs connected by NVLink; put them across an InfiniBand link instead and the communication cost dwarfs the compute almost immediately, given how constantly they talk. Data-parallel replicas, by contrast, only need to synchronize once per training step — the gradient all-reduce — so they can tolerate sitting across the slower inter-node InfiniBand link without it dominating the step time. This is exactly why real training runs place tensor parallelism inside a node and data parallelism (and typically pipeline parallelism) across nodes — the callback to page 23's four parallelism strategies, now with the hardware reason attached to where each one physically goes.

10Collective communication and ring all-reduce

Multi-GPU training relies on a small set of standard communication patterns, called collectives, that every distributed training framework implements. Broadcast sends the same data from one GPU to every other GPU. Reduce combines data from every GPU — typically by summing — down onto one destination GPU. All-reduce combines data from every GPU and gives every GPU the combined result, which is exactly what gradient synchronization needs: every replica needs the same averaged gradient. All-gather has each GPU holding a different piece of data, and ends with every GPU holding all the pieces, concatenated. Reduce-scatter combines data from every GPU, but splits the combined result so each GPU ends up with only its own slice of it rather than the whole thing. All-reduce, in practice, is usually implemented as a reduce-scatter followed by an all-gather — which is exactly how ring all-reduce is built.

Arrange the N GPUs participating in an all-reduce in a logical ring — each GPU has exactly two neighbors, one it sends to and one it receives from. Split each GPU's local data (its gradients) into N chunks. The scatter-reduce phase runs for N−1 steps: at every step, every GPU simultaneously sends one chunk to its right-hand neighbor and receives a chunk from its left-hand neighbor, adding the received chunk into its own copy of that same chunk index, and the chunk index being passed rotates each step. After N−1 steps, every GPU holds the fully-reduced sum for exactly one chunk index — a different one per GPU. The all-gather phase then runs for another N−1 steps, using the same ring, except now each GPU just relays its already-final chunk onward instead of adding to it, until every GPU has received every chunk in its fully-reduced form. The key property, at every single step of both phases: each GPU only ever sends and receives one chunk's worth of data — a bounded amount, independent of how many GPUs total are in the ring.

11The math: ring all-reduce's communication cost

$$\text{Data moved per GPU} \approx \frac{2(N-1)}{N} \times S$$
  • N the number of GPUs participating in the ring.
  • S the size of the data being all-reduced — for gradient synchronization, the total size of the gradients.
  • 2(N-1)/N N−1 steps of scatter-reduce plus N−1 steps of all-gather, each step moving 1/N of the data — total $2(N-1) \times S/N$ per GPU.
  • The limit as N grows large, $2(N-1)/N \to 2$ — a constant, not something that scales with the number of GPUs.

That limit is the elegant part. Doubling your GPU count doesn't double each GPU's communication burden — it stays roughly flat, approaching twice the data size and never exceeding it, no matter how large the ring gets. Compare that to a naive centralized parameter server: every one of the N workers has to send its gradients to the server, and the server has to send updated weights back to all N workers, all through that one server's network link. That link's traffic grows linearly with N — it becomes the exact bottleneck you're trying to scale past, precisely as you add more GPUs to go faster.

12Why this hardware, and why this algorithm

Why SIMT hardware fits dense matrix math specifically: a matrix multiply's output elements are all independent of each other, computed by the same operation — multiply, accumulate, repeat — with no data-dependent branching anywhere in the computation. That's precisely the one constraint SIMT hardware is built around: thousands of simple cores, no branch-prediction machinery, all executing the same instruction across different data every cycle. A CPU's expensive control-flow logic exists to handle exactly the kind of unpredictable, data-dependent branching that dense matrix math simply doesn't have — which means, for this specific workload, a CPU is paying for hardware capability it never uses, while a GPU is spending its entire chip budget on exactly the capability the workload needs.

Why ring all-reduce beats a naive centralized parameter server: a star topology, with every worker talking to one central server, funnels all N workers' traffic through a single network link. That link has a fixed bandwidth ceiling, so the time to synchronize grows with N — the more GPUs you add to speed up training, the worse that one link's congestion gets, which is the opposite of what you want from adding hardware. Ring all-reduce distributes the communication load evenly across every link in the ring instead of concentrating it on one node — there's no single point where traffic piles up. It isn't entirely free: with more GPUs in the ring there are more steps to complete, since scatter-reduce and all-gather each take N−1 hops. But the resource that was actually the bottleneck — bytes any single GPU has to push through its own link — stays close to constant. That's the trade that makes large-scale data-parallel training's gradient synchronization scale gracefully instead of collapsing under its own communication cost.

13Tradeoffs, and what actually breaks

LatencyLowestLow — purpose-built for HPC / RDMAHigher, more protocol overhead

Three failure modes worth naming explicitly, because they show up in real kernels and real clusters, not just in theory. Warp divergence from branch-heavy code silently halves or worse a kernel's effective throughput — every diverging branch means the warp pays for both paths while only ever benefiting from one, and it's easy to write correct CUDA or Triton code that divergences without realizing it. Low occupancy from register or shared-memory pressure is a quieter failure — the kernel still produces correct results, it's just slower than it should be, because the SM doesn't have enough resident warps to hide memory latency behind, so cores sit idle waiting on HBM instead of doing useful work for another warp. And communication becoming the bottleneck when interconnect topology doesn't match your parallelism strategy is a cluster-design failure, not a kernel one — put tensor-parallel shards across InfiniBand instead of NVLink, or fail to keep pipeline-parallel stage boundaries aligned with node boundaries, and you can end up with GPUs that are individually fast sitting mostly idle waiting on the network, which defeats the entire point of adding more of them.

14Worked example and a production use case

Illustrative ring all-reduce walkthrough — 4 GPUs, toy numbers

Take 4 GPUs in a ring: GPU0 → GPU1 → GPU2 → GPU3 → back to GPU0. Each GPU's gradient vector is split into 4 chunks (N=4), and follow just one chunk index through the scatter-reduce phase — say GPU0 holds the value 2 for this chunk, GPU1 holds 5, GPU2 holds 3, GPU3 holds 8 (illustrative, made up for this walkthrough). Step 1: GPU0 sends its 2 to GPU1, which adds it to its own 5, holding 7. Step 2: GPU1 sends that 7 to GPU2, which adds it to its own 3, holding 10. Step 3: GPU2 sends that 10 to GPU3, which adds it to its own 8, holding 18 — the true sum, 2+5+3+8=18, and for now it lives only on GPU3. That's 3 steps, N−1 for N=4, exactly as the formula predicts. Meanwhile, the other 3 chunk indices are rotating through the exact same pattern simultaneously, each one fully reducing onto a different GPU by the end of its own 3 steps — scatter-reduce is done, and each of the 4 GPUs now holds the true sum for exactly one of the 4 chunks. All-gather then runs the same ring pattern for 3 more steps, except each GPU now just relays its already-final chunk onward instead of adding to it, until all 4 GPUs hold all 4 fully-reduced chunks — the complete, synchronized gradient, on every GPU, with no GPU ever having sent or received more than 3 chunks' worth of data in total across the whole process.

Production use case: designing GPU cluster topology for a large training run

Say you're laying out a training job across a cluster with several GPUs per node, connected by NVLink within a node and InfiniBand between nodes. The placement decision follows directly from the communication-frequency argument in this page: tensor parallelism — which needs to communicate within every layer — goes on the GPUs connected by NVLink, meaning it stays confined inside a single node, sized to however many GPUs that node has. Pipeline parallelism, which only needs to pass activations at stage boundaries, can cross the slower InfiniBand link between nodes without it dominating step time. Data parallelism — replicating that whole tensor-parallel-plus-pipeline-parallel unit and synchronizing gradients once per step via ring all-reduce — is the layer that scales across as many of those units as you have, tolerating the InfiniBand link because ring all-reduce keeps each individual GPU's communication burden bounded regardless of how many replicas you add. Get this placement backwards — say, splitting a single layer's weights tensor-parallel-style across an InfiniBand link — and the cluster's raw compute capacity stops mattering, because the GPUs spend most of their time waiting on the network rather than computing.

15Interview questions

BeginnerWhy are GPUs so much faster than CPUs for deep learning?

A GPU uses SIMT architecture — thousands of simple cores executing the same instruction across different data simultaneously — instead of a CPU's handful of complex cores built with extensive branch-prediction and control-flow hardware. Deep learning is overwhelmingly dense matrix multiplication and elementwise operations: every output element is computed independently, by the same operation, with essentially no data-dependent branching. That's an embarrassingly parallel workload with no need for the control-flow machinery a CPU spends most of its silicon on, and it's exactly the shape SIMT hardware was built to execute — thousands of cores doing the same multiply-accumulate at once, rather than a few cores each handling their own complicated, branchy sequence of instructions.

BeginnerWhat is a warp, and what happens when threads inside one diverge?

A warp is a group of 32 threads that the GPU always schedules and executes together, running the identical instruction at the identical time on different data — the actual physical unit of SIMT execution, one level below the thread block. Warp divergence happens when threads within a warp need to take different branches of an if/else. Since a warp can only run one instruction stream across all its lanes at a time, the hardware serializes the branches: it runs the "if" path across the whole warp with the threads that shouldn't take it masked off, then runs the "else" path across the whole warp with the other threads masked off. Every thread sits through both passes, but only half the work in each pass is useful — which is why branch-heavy, data-dependent code is slow on a GPU.

IntermediateWhat is Triton, and why would you reach for it instead of hand-written CUDA?

Triton is a Python-embedded language and compiler for writing GPU kernels at the level of tiles or blocks of data rather than individual threads. Writing genuinely efficient CUDA by hand requires deep, specialized expertise in coalesced memory access, register and shared-memory budgeting for occupancy, and manual thread-indexing math — a real cost most ML researchers, who think in tensors and layers rather than threads and warps, don't have time to pay for every new idea. Triton's compiler automatically handles that low-level thread scheduling, memory coalescing, and shared-memory allocation, getting most of hand-tuned CUDA's performance for a fraction of the development time. FlashAttention's efficient reference implementation is written in Triton, and a large share of PyTorch's own generated custom kernels are Triton kernels, for exactly this reason.

IntermediateWhat's the practical difference between NVLink and InfiniBand, and why does it drive where you place different parallelism strategies?

NVLink connects GPUs on the same physical node at very high bandwidth, built specifically for direct GPU-to-GPU communication. InfiniBand (or RoCE) connects separate nodes — still fast and purpose-built for HPC clusters, but roughly an order of magnitude or more below NVLink's bandwidth. Tensor parallelism communicates within every single layer, many times per forward and backward pass, so it needs to live on NVLink-connected GPUs inside one node — putting it across InfiniBand would make communication dominate almost immediately. Data parallelism only synchronizes gradients once per step, so it can tolerate sitting across the slower InfiniBand link between nodes without that link becoming the bottleneck.

DeepExplain ring all-reduce, and why it scales better than a naive centralized approach.

Arrange N GPUs in a logical ring, split each GPU's gradient data into N chunks, and run two phases: scatter-reduce, N−1 steps, where each GPU sends one chunk to its ring-neighbor and accumulates a chunk received from its other neighbor, ending with every GPU holding the true sum for exactly one chunk; then all-gather, another N−1 steps, relaying each GPU's already-final chunk around the ring until every GPU has every chunk. At every step, each GPU only ever sends and receives one chunk — a bounded amount of data, independent of N. Total data moved per GPU works out to roughly 2(N−1)/N times the data size, which approaches a constant (2×) as N grows rather than scaling with cluster size. A naive centralized parameter server, by contrast, funnels every worker's traffic through one server's network link, whose bandwidth ceiling is fixed — so synchronization time grows linearly with the number of workers, becoming the exact bottleneck you're trying to scale past by adding more GPUs.

DeepYou're handed a cluster with several GPUs per node on NVLink, and InfiniBand between nodes. How do you lay out tensor, pipeline, and data parallelism across it, and why?

Tensor parallelism goes inside a node, on the NVLink-connected GPUs, because it communicates partial results within every layer — many times per forward and backward pass — and needs the fastest possible link or that communication dominates the compute. Pipeline parallelism can cross the InfiniBand link between nodes, since it only passes activations at stage boundaries, which is far less frequent and far more tolerant of a slower link. Data parallelism replicates the whole tensor-parallel-plus-pipeline-parallel unit across as many groups of nodes as you have, synchronizing gradients once per step via ring all-reduce over InfiniBand — tolerable specifically because ring all-reduce keeps each GPU's communication burden bounded regardless of how many replicas you add. Getting this backwards — for instance splitting a single layer tensor-parallel-style across InfiniBand — turns the network into the bottleneck and leaves the GPUs' raw compute capacity mostly unused, since they'd spend most of their time waiting on data that has to cross the slower link on every layer.
