Evaluation, Reliability & Safety

A test-set accuracy number answers "did it do well on questions like these." It says nothing about the question nobody thought to ask. This page is the discipline of finding that question before a user, an attacker, or a regulator does.

Know cold ~23 min · prerequisites: calibration basics (01), RAG/agent loop (11) — 11 already covers RAG-specific evaluation and prompt-injection in the agent context
TL;DR

Evaluation isn't one number, it's a portfolio of different questions, because a model can fail in categorically different ways: it can be confidently wrong (calibration), fragile to inputs slightly unlike its training data (robustness), factually wrong while sounding fluent (hallucination), exploitable by someone feeding it adversarial input (security), or simply opaque about why it did what it did (interpretability). LLM-as-judge and pairwise preference comparison exist because human evaluation doesn't scale to the volume modern systems need, but they inherit real, well-documented biases — position, verbosity, self-preference — that you mitigate, not eliminate. Red-teaming and monitoring are continuous, not a pre-launch gate, because new failure modes and attacks are discovered after launch, not before. One sentence for an interview: every evaluation method on this page is a proxy for "will this behave well on cases I haven't seen," and the discipline is knowing which proxy's blind spots matter for your specific system.

01Where this sits in the timeline

Evaluation used to be the easy part. It stopped being easy exactly when models stopped producing a single verifiable number as their output.

Before

Classical ML evaluation was static and closed-form: hold out a test set, compute accuracy, F1, or MSE once, and that number was the answer. It worked because the task had one correct answer per example, computable automatically, and the test set could be trusted to resemble production data reasonably well.

→
Innovation

Three things broke that model at once. Open-ended generation (an LLM's response to "explain photosynthesis") has no single correct string to match against, which is what pushed the field toward LLM-as-judge and pairwise human/model preference comparisons instead of exact-match scoring. Web-scale pretraining meant benchmarks themselves — published on the same internet the model trained on — started leaking into training data (contamination), quietly inflating scores on tests that were supposed to be held out. And agentic systems that take multi-step actions made "was the final answer right" insufficient — a trajectory can reach the right answer through a dangerous or wasteful path, so the whole trajectory needs evaluating, not just its last step.

→
After

Modern practice treats reliability as multi-dimensional and ongoing: benchmark scores plus calibration plus robustness testing plus continuous red-teaming plus production monitoring, running in parallel, indefinitely — not a single pre-launch checkbox. The shift in mindset is from "did it pass the test" to "how do we keep finding the ways it fails."

02The intuition, before any math

You cannot fully test a system against failure modes you haven't imagined yet. Every technique on this page is a different strategy for imagining more of them, faster than an attacker or an unlucky user does.

Here's the uncomfortable core fact: a model's performance on its test set tells you how it behaves on inputs statistically similar to that test set. It tells you nothing directly about inputs that are subtly different (distribution shift), deliberately adversarial (an attacker crafting input specifically to break it), or simply rare enough that they never showed up in a few thousand held-out examples. The test set is a sample of "questions like these," and the entire point of evaluation-as-a-discipline is that "questions like these" is never the full space of questions a deployed system will actually receive.

This reframes what all of these techniques are actually for. Robustness testing and adversarial examples are a deliberate search for inputs near the edge of what the model handles well. Red-teaming is a deliberate search for inputs a malicious user would craft. Calibration asks the model to at least know when it's in unfamiliar territory, even if it can't always get the answer right. Interpretability asks what the model is actually computing internally, so you're not purely relying on input-output behavior to guess at failure modes you haven't triggered yet. None of these give you a proof that the system is safe — they give you a wider net for finding the ways it isn't, before those ways find your users.

03The landscape: five questions, five toolkits

Eighteen distinct concepts sounds unmanageable until you notice they cluster into five different questions being asked about a model. Keep the grouping, not the list, in your head.

1. How do you measure quality when there's no single right answer?

Benchmark design and contamination. A benchmark is only informative if the model hasn't already seen its answers during training. Contamination — benchmark questions and answers leaking into a pretraining corpus scraped from the same public internet the benchmark was published on — is a real, documented problem for web-scale LLMs, and it inflates scores silently: nothing errors, the number is just meaningless. Detection strategies include n-gram overlap checks between training data and benchmark text, canary strings deliberately inserted into a benchmark to see if a model has memorized them, and comparing performance on a benchmark's public version against a held-back, never-published variant of similar difficulty.

Calibration and uncertainty. A model is calibrated if its stated confidence matches its actual accuracy — when it says "80% confident" across many predictions, it should be right about 80% of the time. Modern neural networks are frequently overconfident by default; temperature scaling (dividing logits by a learned scalar before softmax) is the standard practical fix, already covered in depth on 01. What's specific to this page: calibration is itself an evaluation target you measure, not just a training-time fix, using the Expected Calibration Error metric below.

LLM-as-judge. Use a strong LLM to score or compare another model's open-ended output against a rubric, since exact-match scoring doesn't work for free-form text and human evaluation doesn't scale to continuous, high-volume testing. It works well enough to be genuinely useful — but it has specific, well-documented failure modes: position bias (favoring whichever answer appears first or second in a pairwise comparison, regardless of quality), verbosity bias (rewarding longer answers independent of correctness), and self-enhancement bias (a judge scoring outputs from its own model family more favorably). Mitigations are mechanical, not magical: randomize answer order and average across orderings to cancel position bias, use a judge from a different model family than the one being evaluated, and use multiple judges rather than one.

Pairwise preference evaluation. Instead of asking a judge for an absolute score ("rate this 1–10"), ask which of two outputs is better. Relative judgments are consistently more reliable than absolute ones — it's a documented pattern in human preference research as well as LLM-judge research — which is also exactly why RLHF preference data (see 15) is collected as pairwise comparisons in the first place, not absolute scores.

Agent trajectory evaluation. An agent doesn't produce one output — it produces a sequence of tool calls, observations, and intermediate decisions (the ReAct-style loop from 11). Grading only the final answer misses failures mid-trajectory: reaching the right answer via an unsafe action, an unnecessarily expensive sequence of tool calls, or getting lucky after an early wrong turn. Trajectory evaluation checks the path, not just the destination — harder, because unlike a single output there are usually many valid paths to a correct outcome, so "did it match a reference trajectory" is often the wrong question; "was every step reasonable given what the agent knew at that point" is closer to the right one.

2. Does it still work on inputs unlike its training data?

Robustness to distribution shift. Performance measured on data statistically different from training data — a new time period, a new demographic, a new phrasing style users adopt after launch. This is the single most common way production models degrade: quietly, with no crash, no error, no code change, just an input population that's drifted away from what the model was validated on.

Adversarial examples. Small, often imperceptible, deliberately crafted perturbations that flip a model's prediction — the classic case is an image, altered by an amount invisible to a human, that a classifier suddenly misclassifies with high confidence. For LLMs, the analogous attack is an adversarial suffix or crafted phrasing engineered to manipulate output. What makes these different from ordinary distribution shift is intent: someone specifically searched for the input that breaks you.

OOD detection. Recognizing when an input is unlike anything the model was trained on, so the system can abstain, flag for human review, or express low confidence — rather than confidently emitting a wrong answer as if it were a normal case. This is the practical, deployable complement to calibration: calibration asks the model to know its confidence is low; OOD detection asks the system to catch the case entirely, ideally before the model even has to guess.

Fairness and subgroup evaluation. An aggregate accuracy number can look fine while hiding a large performance gap for a specific subgroup — computing metrics sliced by group (by demographic, by region, by device type) is the only way to catch that a "97% accurate" model is actually failing 40% of the time for one particular slice of users. A genuinely hard result worth knowing: several intuitive fairness definitions (equal false-positive rates across groups, equal calibration across groups, equal overall accuracy) can be mathematically incompatible with each other except in special cases — you generally cannot satisfy all of them simultaneously, so "make the model fair" always requires picking which fairness definition actually matters for the decision at hand.

3. Can you trust what it says?

Hallucination and factuality. LLMs are trained to produce fluent, plausible continuations, not to fact-check themselves — fluency and truth are correlated in training data but not the same objective, which is exactly why a model can generate a confident, well-formatted, entirely fabricated citation. Hallucination isn't a bug that a bigger model necessarily removes; it's a direct consequence of the training objective, which is why mitigation leans on retrieval grounding and verification rather than scale alone.

Groundedness and citation correctness. Specific to retrieval-augmented systems (11): checking that a claim in the generated answer is actually supported by the retrieved source it's attributed to, not just plausible-sounding text near a citation marker. A groundedness checker (often another LLM call, or a dedicated smaller classifier) compares each claim against the retrieved passages it's supposed to be based on — this catches the specific and common RAG failure where retrieval succeeded but generation still drifted away from what was actually retrieved.

4. Can someone break it on purpose?

Red teaming. Deliberately trying to elicit harmful, unsafe, or undesired behavior from a system before real adversaries do — using human testers, automated adversarial generation, or both. It has to be continuous, not a one-time pre-launch gate, because new jailbreak techniques are discovered constantly after launch; a system red-teamed thoroughly in January is not necessarily still safe against attacks discovered in June.

Prompt injection and tool security. A prompt injection hides instructions inside content the model processes — a webpage, a document, an email — that hijack the model's behavior when it treats embedded text as instructions rather than as data to reason about. This is a serious, distinct risk for agentic and tool-using systems specifically (see the ReAct loop on 11): an agent that reads a webpage as part of a task can have its actual goal silently overwritten by text on that page, and because the "attack" is just ordinary-looking text, it's far harder to filter than a malicious API payload would be.

Data poisoning and model extraction. Poisoning is an attacker manipulating training data — inserting examples designed to implant a backdoor (a hidden trigger that causes specific misbehavior) or bias the model's behavior in a chosen direction. Extraction is the inverse direction: an attacker repeatedly queries a deployed model to reconstruct a functional copy of it, or to recover memorized details of its training data, without ever accessing the weights directly.

Privacy leakage. Models can memorize specific training examples and later regurgitate them, verbatim or near-verbatim, when queried in particular ways — a genuine risk when training data includes personal or sensitive information, since the model didn't "learn a pattern" from that example so much as store it outright.

5. What is it actually computing, and can you steer it?

Saliency, probing, activation analysis. Saliency methods attribute an output back to input features — which pixels, which tokens most influenced this specific prediction — usually via gradients or perturbation. Probing trains a small auxiliary classifier on a model's internal activations to test whether specific information (part of speech, sentiment, a fact) is linearly recoverable from that layer, which tells you what's represented even if you don't know how it's used. Both are useful and both have a real limitation worth stating plainly: a saliency map can look plausible while not actually reflecting the computation that caused the output — it's a correlational tool, not a proof of causation.

Mechanistic interpretability. A more ambitious research program: reverse-engineer the actual algorithm a network has learned internally, in the way you'd reverse-engineer a compiled program back into readable source — finding specific circuits (subsets of attention heads and neurons across layers) responsible for a specific capability or behavior, rather than only correlating activations with outputs. It's a young, active research area, not yet a routine production tool, but it's the direction the field is heading if "we don't really know why it did that" stops being an acceptable answer for high-stakes systems.

Safety alignment and controllability. Making a model's behavior reliably match intended values and constraints (the RLHF/DPO machinery from 10 and 15 is the primary current tool), and separately, ensuring humans retain a meaningful ability to correct, constrain, or halt undesired behavior after deployment — alignment at training time and controllability at run time are related but distinct goals, and a system can have one without fully having the other.

The evaluation loop — why it never actually stops
There is no terminal "passed" state. A model that cleared every stage still gets re-tested on the next model change, the next distribution shift, and the next attack technique discovered after launch — the arrow back to the start is the point, not an edge case.

04The math that's actually load-bearing here

$$\text{ECE} = \sum_{b=1}^{B} \frac{|S_b|}{n} \left| \text{acc}(S_b) - \text{conf}(S_b) \right|$$
  • Expected Calibration Error bucket predictions into $B$ bins by their predicted confidence (e.g. 0–10%, 10–20%, …), then for each bin $S_b$ compare the bin's actual accuracy against its average stated confidence, weighted by how many predictions fall in that bin.
  • acc(S_b) the fraction of predictions in that confidence bin that were actually correct.
  • conf(S_b) the average predicted confidence of predictions in that bin.
  • Reading it ECE near zero means confidence tracks reality — the model's "80% sure" predictions really are right about 80% of the time. A large ECE means the model is systematically over- or under-confident, and temperature scaling (01) is the standard fix once you've measured it.

For agreement between two raters — two human annotators, or a human checked against an LLM judge — plain percent agreement overstates reliability, because two raters agree by pure chance some of the time (more often still if one label is common). Cohen's kappa corrects for that: $$\kappa = \frac{p_o - p_e}{1 - p_e}$$ where $p_o$ is observed agreement and $p_e$ is the agreement expected purely by chance given each rater's label distribution. A kappa near 0 means the raters are barely doing better than chance; near 1 means they agree almost perfectly beyond what chance alone would produce. This is the right tool for the question "does my LLM judge actually agree with my human evaluators, or does it just look that way because it always picks the more common label."

And for any binary safety classifier — a jailbreak detector, a content filter, a red-team success/fail label — the same precision/recall tradeoff from 01 applies directly: a filter tuned to catch nearly everything unsafe (high recall) will also flag legitimate content as unsafe more often (lower precision), and a filter tuned to rarely bother legitimate users (high precision) will let more genuinely unsafe content through (lower recall). There is no threshold that maximizes both simultaneously — deciding which error is more expensive for your specific system is a product decision, not a modeling one.

05Why this design, not the obvious alternative

Why trust an LLM to judge another LLM, given the known biases? Because the alternative — exhaustive human evaluation of every model change, at the volume modern systems iterate at — simply doesn't scale, and the biases are mitigable rather than fatal. Position bias cancels out if you randomize order and average; self-enhancement bias is reduced by judging with a model from a different family than the one under test; verbosity bias is caught by including it explicitly as a rubric criterion rather than leaving "quality" undefined. Used carefully, with known mitigations applied and human spot-checks retained as a sanity check rather than replaced entirely, LLM-as-judge is a genuinely useful scalable proxy — not a perfect one, a useful one, which is a different and more honest claim.

Why pairwise comparison instead of absolute scoring? Asking "is A better than B" is a much easier, more consistent judgment to make — for both humans and LLM judges — than asking "rate this response 7 out of 10," because an absolute scale has no fixed anchor and different raters silently use different internal scales for what a "7" means. Relative comparisons sidestep that entirely: you don't need to agree on what a 7 means, only on which of two concrete things is better.

Why red-team continuously instead of once before launch? Because the set of known attacks is not fixed. A model considered safe against every jailbreak technique known in January can be broken by a technique discovered in June — the attack surface evolves after deployment, the same way a security system's threat model doesn't freeze the day it ships. Treating red-teaming as a one-time gate is treating an adversarial, ongoing process as if it were a static test — a category error that shows up in production as a surprise, not a slow, easy-to-catch trend.

06Complexity, failure modes, and what actually breaks

Silent contamination

A benchmark that's leaked into training data doesn't fail loudly — it produces an inflated, meaningless score that looks like genuine progress. The only way to catch it is actively checking for overlap between training data and benchmark content, or holding back a fresh, never-published variant to compare against; a suspiciously high score alone is not proof, but it's a reason to check.

LLM-judge biases compound with model updates

If your judge model and your system-under-test are both updated over time, self-enhancement bias can silently shift — a judge from a newer model family might start favoring outputs that share that family's stylistic quirks, making "quality improved" and "outputs got more judge-flattering" indistinguishable without a periodic human-eval check to recalibrate against.

Fairness metrics can conflict by construction

Because several reasonable fairness definitions are mathematically incompatible except in special cases, "make it fair" is underspecified until you pick which definition matters for the decision — equal error rates across groups and equal calibration across groups can be in direct tension, and satisfying one can require violating the other.

Saliency maps can mislead confidently

A saliency map highlighting "the features that mattered" is a correlational attribution, not a proof of the model's actual causal computation — it can look clean and interpretable while not accurately reflecting why the model actually produced that output, which is exactly the gap mechanistic interpretability is trying to close by studying the computation itself rather than only its attributed inputs.

Prompt injection doesn't look like an attack

Because the "malicious payload" is just ordinary-looking text on a webpage or in a document, standard input sanitization (built for detecting code injection, SQL injection, and similar structured attacks) doesn't generalize to catching it — the content is entirely well-formed natural language, which is precisely what makes it hard to filter without also filtering legitimate instructions.

07Worked example and a production use case

Illustrative ECE calculation

Say a classifier makes predictions that fall into three confidence bins (illustrative numbers): 100 predictions at ~90% stated confidence, of which 80 are actually correct (accuracy 0.80, gap 0.10); 60 predictions at ~70% confidence, of which 45 are correct (accuracy 0.75, gap 0.05 — this one's fine); and 40 predictions at ~50% confidence, of which 34 are correct (accuracy 0.85, gap 0.35, badly under-confident here). Weighting each bin's gap by its share of the 200 total predictions: $(100/200)(0.10) + (60/200)(0.05) + (40/200)(0.35) = 0.05 + 0.015 + 0.07 = 0.135$. An ECE of roughly 0.135 (illustrative) says this model's stated confidence is off by about 13.5 percentage points on average — enough to be worth a temperature-scaling pass before trusting its confidence scores for anything downstream, like an abstention threshold.

Production use case: shipping a prompt change safely

Say a team wants to change a chatbot's system prompt and needs to know if it's actually an improvement before rolling it out to all traffic. The practical pipeline: run both prompt versions against a fixed set of representative queries, generate a response from each, then use pairwise LLM-as-judge comparison (order-randomized, judged by a model from a different family than the one being tested) to get a preference rate between old and new. Spot-check a random sample of the judge's calls with actual human review — not to replace the judge, but to catch systematic judge errors before trusting the aggregate number. If the new prompt wins clearly and the human spot-check agrees with the judge's calls, roll out to a small percentage of real traffic (a canary), watching production metrics — actual user engagement, escalation rate to a human agent, explicit user feedback — before widening the rollout. The judge comparison tells you it's probably better in the way you tested; the canary tells you it's actually better in the way that matters, on traffic you didn't specifically construct.

08Interview questions

BeginnerWhat does it mean for a model to be "calibrated," and how would you measure it?

A calibrated model's stated confidence matches its actual accuracy — when it says 80% confident across many predictions, it's right about 80% of the time. You measure it with Expected Calibration Error: bin predictions by confidence, compare each bin's average confidence against its actual accuracy, and take the weighted average of that gap across bins. Neural networks tend to be overconfident by default; temperature scaling — dividing logits by a learned scalar before softmax — is the standard fix, applied after training without changing which class gets predicted, only how confidently.

BeginnerHow would you detect that a benchmark has been contaminated by training data?

A few converging signals, none conclusive alone: check for direct n-gram overlap between the benchmark's text and the training corpus; insert canary strings into a benchmark and check whether the model can reproduce them verbatim, which it shouldn't be able to do if it never saw them; and compare performance on the published benchmark against a fresh, never-released variant of similar difficulty — a large, unexplained gap between the two is a strong signal the published version leaked in.

IntermediateWhat are the known failure modes of LLM-as-judge, and how do you mitigate each?

Position bias — favoring whichever answer appears first or second regardless of quality — mitigated by randomizing order and averaging across orderings. Verbosity bias — rewarding length over correctness — mitigated by making conciseness or specificity an explicit rubric criterion instead of leaving "quality" undefined. Self-enhancement bias — a judge favoring outputs from its own model family — mitigated by using a judge model from a different family than the system under test. None of these are fully eliminable, which is why periodic human spot-checks against the judge's calls remain part of a responsible pipeline rather than a one-time validation step.

IntermediateWhy evaluate an agent's full trajectory instead of just its final answer?

An agent can reach a correct final answer through a path that was unsafe, wasteful, or lucky — e.g. it might delete and recreate a file to "fix" something when a safer edit existed, or make ten redundant tool calls to arrive at an answer a well-designed agent would reach in two. Grading only the final output misses all of that. Trajectory evaluation instead checks whether each step was reasonable given what the agent knew at that point — harder than final-answer grading because there's often more than one valid path to a correct outcome, so you're judging reasonableness of the process, not matching against one canonical reference trajectory.

IntermediateExplain indirect prompt injection and why it's hard to defend against.

An attacker embeds instructions inside content the model will process as part of a task — a webpage, a document, an email — rather than sending the model instructions directly. When an agent reads that content (say, to summarize a webpage) and the model doesn't reliably distinguish "text I should reason about" from "text telling me what to do," the embedded instructions can hijack its behavior. It's hard to defend against because the payload is just ordinary, well-formed natural language — there's no malicious syntax pattern to pattern-match against the way there is for SQL injection — so mitigation leans on architectural separation (clearly marking retrieved content as untrusted data, restricting what actions an agent can take based on content it merely read) rather than input filtering alone.

DeepDesign an evaluation pipeline for a new agentic coding assistant feature before launch. Walk through it.

Start with offline trajectory evaluation on a fixed suite of representative coding tasks — did it reach a correct, working solution, and separately, was the sequence of tool calls and edits reasonable (no destructive actions, no wasted steps) along the way. Add adversarial/red-team probes specifically for this feature: prompts trying to get it to run destructive commands, exfiltrate data, or ignore explicit user constraints. Add LLM-as-judge pairwise comparison against the previous version of the assistant on a broad query set, with human spot-checks on a sample. Before full rollout, run a canary with a small percentage of real users, monitoring for escalations, explicit negative feedback, and any destructive-action reports. Post-launch, keep red-teaming continuously rather than treating the pre-launch pass as final — new jailbreak and injection techniques targeting coding agents specifically are an active, evolving area, not a solved problem you test once.

DeepYour LLM-judge pairwise eval shows the new model version winning 65% of comparisons (illustrative), but a few users are reporting the new version feels worse. What do you check?

First, check for judge bias explaining the gap: is the new model simply more verbose, and is verbosity being rewarded rather than controlled for in the rubric? Is the judge from the same family as the new model, creating self-enhancement bias? Second, check the query distribution: the judge's comparison set may not represent the specific query types the complaining users are sending — a model can win in aggregate while regressing on a specific, underrepresented but important slice, which is exactly the subgroup-evaluation problem applied to query types instead of demographics. Third, do a targeted human review specifically on the query types the complaints are about, rather than trusting the aggregate win rate to generalize to every slice equally — an aggregate number, like an aggregate accuracy, can hide a real regression in a subset that matters.
